# Application-wide adoption of the Appearance screen's system design

## Problem
The maintainer chooses AppearanceSettings as the reference for every screen.
Its List/Section/Picker/Toggle and navigation are already system-rendered. Avoid
replacing those controls with decorative glass or changing domain behavior.

## Solution
Apply a shared system presentation policy at the app root, themed screens and
sheet boundaries. Preserve explicit specialized list/button styles in descendants.
Replace remaining legacy command-panel backings, the custom avatar sheet on iOS
26, and missing member/invitation navigation. Cover every Shared/Views source in
a reproducible inventory, distinguishing content renderers from screen roots.

## Technical design
- Native grouped list/form defaults and contextual automatic controls, as in the
  reference; no app-wide glass button style and no material on message rows.
- System automatic toolbar materials and automatic scroll-edge effects; retain
  explicit specialized overrides. iOS 15 fallback unchanged.
- System sheet presentation for the avatar menu on iOS 26, keeping its bindings,
  switching, nested sheet routing and privacy behavior.
- Native button styling for shared onboarding/confirmation actions, preserving
  disabled state and all original callbacks.
- Keep custom data/content renderers, call/video canvases, security input and
  photo gestures. Shared system chrome applies without rewriting their logic.

## Steps
1. Inventory all view source files and remaining hidden-navigation/material paths.
2. Install shared policy through root/theme/sheets and update exceptional controls.
3. Verify every hidden-navigation occurrence has a replacement or documented reason.
4. Compare business functions and security/session paths against baseline.
5. Update product/spec/impact and inventory; review twice; compile the tagged build.

Threat model: presentation changes must preserve local-auth redaction, biometric
gates, active-call/recording gestures, permission checks and destructive alerts.
No global UIKit appearance mutation or private API. Device-wide appearance checks
cannot be inferred from a source inventory or a successful compile. Two plan
reviews found no contradiction with the reference or preservation requirements.

## Review corrections and verification scope
- Queue avatar-menu destinations until system sheet onDismiss; preserve redaction
  and use a scrollable large detent for accessibility content.
- Propagate the original button role as well as its trigger in the native primary
  style. Retain external disabled checks and keep isDisabled display-only.
- Register the shared UI implementation in the separate share-extension target.
- Keep root authorization/database initialization and all API callbacks unchanged.
- Inventory contains 187 sources, including renderers/helpers; this is not a count
  of screens or evidence of visual testing. Remaining hidden bars are documented.

## Static review outcome
Two subsequent review passes found no further scope, data-flow or documentation
issue. The reference screen is byte-identical. App initialization/theme logic,
consent actions, member operations, search resolution, popup callbacks, password
and redaction guards were compared against baseline. Model/core/crypto sources
are unchanged. Both target source registrations and spec links were checked.
Inventory and offline notices match. CI compile and device validation are pending;
this is not a claim of a complete UIKit rewrite or every-route visual verification.
