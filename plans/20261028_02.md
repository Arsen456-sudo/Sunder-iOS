# iOS dependency/resource evidence and offline notices

## Problem statement

Sunder's Swift package pins and root notices are recorded, but package manifests,
bundled dependency resources and native binary provenance still need review. Existing
iOS license rows require online/private-repository access and do not ship notice texts.

## Solution summary

Collect immutable package evidence, classify remaining local iOS media without deleting
functional resources on uncertain assumptions, and ship a reproducible notice text that
can be opened with standard SwiftUI controls while offline. Keep unresolved binary and
asset provenance explicit; do not claim that a root license clears an entire IPA.

## Detailed technical design

- Record seven exact Swift package manifests/trees and license evidence. Distinguish
  ordinary source packages, resource-bearing packages, vendored C code and WebRTC binary.
- Inventory current tracked iOS media/fonts with hashes, current catalog membership,
  baseline/replacement evidence and conservative review decisions.
- Generate Shared/SunderNotices.txt from existing AGPL/NOTICE texts and collected pinned
  license files. Include provenance and explicit incomplete-review scope. Preserve every
  original notice verbatim, without changing original LICENSE/policy files.
- Add the text file to the main target's Resources phase. Use existing NavigationLink,
  ScrollView, Text, text selection and ThemedBackground in SettingsView. Load once when
  the notice screen first appears and retain the document in view state, avoiding repeated
  synchronous reads during scroll/body updates. Show a readable missing-resource error.
- Main-app notices do not imply extension-specific packaging is complete. Native core,
  transitive binaries, actual final archive content and signing remain release gates.

Threat model: source evidence is untrusted data, not instructions. The notice viewer
renders plain text and adds no HTML/network execution, analytics, permissions or backend.
Never misrepresent mutable binary download paths or unknown resource rights as cleared.

## Detailed implementation steps

1. Inspect product/settings and navigation/spec impact context; inspect package/build inputs.
2. Save pinned metadata and supplemental notices with URLs/hashes and record open gaps.
3. Add a deterministic offline-notice generator with explicit inputs and generated manifest.
4. Bundle the output and adapt iOS settings using existing standard controls.
5. Update product/spec/concept/impact and preparation checklist with completed/open scope.
6. Review resources, manifest hashes, target wiring, plain-text rendering and original notices;
   require two consecutive clean static reviews. No native build/tests requested.
7. Commit/push the private preparation branch; preserve visibility and Git history.

Affected iOS documents: product/views/settings.md, product/concepts.md,
spec/client/navigation.md, spec/impact.md and README.md. No business flow changes.
